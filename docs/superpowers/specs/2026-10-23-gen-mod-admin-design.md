# GenMod 管理端设计

日期：2026-10-23

本文约定 `gen-mod-admin` 第一期的范围、边界和可验证行为。实现以本文为准。桌面端改动落在 `D:\codetest\gen-mod`，不把 Tauri 应用迁入本仓库。

`gen-mod-admin` 只提供账号、游戏、Skill、版本和文件数据。游戏与 Skill 的绑定、版本与文件的绑定写在数据库里，用文件 id 指向 R2 中的 zip。zip 只是文件本体，不承载关联。桌面端按这些数据调整登录、检查更新、下载解压、选游戏、加载 Skill 和会话行为。

## 1. 背景与目标

`gen-mod` 是 Windows 本地桌面应用。玩家在本机用 AI 做游戏 MOD。项目、会话、记忆和模型 Key 仍在本机。第一期为它增加云端配套后台：账号、游戏管理、官方 Skill 发布，以及桌面端登录后按用户确认拉取官方 Skill。

成功标准：

- 玩家用邮箱和密码注册并登录桌面端，登录后才能进入工作台。
- 管理员在后台创建游戏、创建和更新官方 Skill。
- 桌面端发现新游戏或新 Skill 版本时提示用户，说明更新后果，用户确认后才按文件 id 下载 zip 并解压使用。
- 用户仍可按现有 Skill 目录约定在本机导入 Skill，但不能通过导入创建游戏。

## 2. 范围

第一期包含：

- `gen-mod-admin` pnpm monorepo：Vue 3 管理后台 + Elysia API，只提供数据。
- 同一套账号，角色区分普通用户和管理员。
- 游戏管理、官方 Skill 发布与版本管理。关联存在数据库中。
- 桌面端按接口数据调整：登录、检查更新、确认后下载解压、按游戏加载 Skill、本机导入约束、会话与内容哈希。

第一期不包含：

- 安装包发布、自动更新安装包。
- 邮箱验证、找回密码、邀请码、第三方登录。
- 按用户分配 Skill 或游戏。
- 把桌面工作台迁到浏览器。
- 在 zip 里再放一份清单来表达游戏绑定或版本。不另造 Skill 文件格式；解压后的目录仍按 `gen-mod` 现有 Skill 目录约定（含 `SKILL.md`）。

## 3. 架构与边界

两个仓库，三条运行路径。

`gen-mod-admin` 只有两个应用：

- `apps/admin`：Vue 3 管理后台，用 Workers Static Assets 发布。
- `apps/server`：Elysia API，运行在 Cloudflare Workers 上。账号、角色、游戏、Skill、版本和文件 id 存在 D1；zip 存在 R2。

桌面端继续留在 `gen-mod`。模型调用走用户自己的服务商，不经过本 API。

游戏由管理员单独创建。Skill 在创建时选择一类，选择结果写入数据库：

- **通用 Skill**：不绑定游戏，没有游戏也可以创建。
- **游戏 Skill**：绑定一个已经创建的游戏。没有可选游戏时，不能创建这一类。

Skill 不创建游戏。游戏记录只包含标识、名称和说明。标识和 Skill 名称使用与 `gen-mod` 能力名相同的字符集：小写字母、数字和连字符，长度 1–64，不以连字符开头或结尾，不含连续连字符。

Skill 记录保存：名称、说明、类型、可选的游戏标识，以及现有清单里不放进 zip 的字段：`dependencies`、`excludePaths`、`requiredCommandScripts`、`inspectionFile`。每个版本记录保存：版本号、上传时间、内容哈希、文件 id，以及保存当时上述清单字段的快照。文件 id 是本系统生成的 UUID，作为 R2 对象键。关联和清单字段只存在这些记录里，不写进 zip。

内容哈希与 `gen-mod` 的 `validate` 相同：先对清单快照的 canonical JSON（`category`、`gameId`、`version`、`dependencies`、`excludePaths`、`requiredCommandScripts`、`inspectionFile`）取字节，再按相对路径排序累加每个文件的路径与内容哈希。不使用 zip 容器字节。`category` 由类型映射（通用 → `common`，游戏 → `game`），`gameId` 来自绑定。

| 数据 | 位置 | 谁可以改 |
| --- | --- | --- |
| 账号、角色、游戏、Skill（含清单字段）、版本（含清单快照、内容哈希、文件 id） | D1 | 注册接口、管理员接口 |
| 官方 Skill 的 zip | R2，对象键 = 文件 id | 编辑、上传文件夹或导入 zip 产生新版本；移除版本时删除对应对象 |
| 本机缓存的游戏/Skill 数据、解压后的官方 Skill、用户导入、项目和会话 | 桌面端现有数据目录 | 用户确认后的同步，以及调整后的本机加载逻辑 |

管理后台和 API 是两个 Worker，生产环境放在同一主域名下。后台使用父域 HttpOnly Cookie，桌面端使用访问令牌和刷新令牌。

按 2026-10-28 的部署要求，管理后台作为纯静态资源 Worker，浏览器通过 `VITE_API_URL` 直接请求 API 域名，不经过 `/api` 转发或 Service Binding。API 使用 Elysia 官方 CORS 插件，按 `CORS_ORIGINS` 精确匹配管理端来源并允许携带凭证。生产部署使用 `scripts/deploy.ps1`，GitHub Actions 在默认分支提交后调用同一脚本。

Workers 没有可持久化的本地磁盘。不使用 Postgres，也不把包写在服务器磁盘上。

## 4. 账号与登录

玩家和管理员使用同一套账号。注册只需要邮箱和密码。密码只在服务端保存哈希。

管理员由 Workers 密钥 `ADMIN_EMAILS` 指定。名单里的邮箱在注册或登录时成为管理员，移出名单后下次登录恢复为普通用户。

两边调用同一个登录接口，凭证不同：

- 管理后台使用父域的 HttpOnly Cookie。普通用户可以登录，但打不开游戏管理和 Skill 管理，相关接口返回 403。
- 桌面端使用访问令牌和刷新令牌，保存在本机应用配置中。访问令牌过期后用刷新令牌更换。

桌面端没有有效登录时停在登录页，不进入工作台。本机已有的项目和 Skill 文件仍留在磁盘上，登录成功后再继续使用。

只有服务端明确判定登录凭证无效时，桌面端才回到登录页。令牌刷新遇到网络或服务错误时留在当前页面并提示，不清除登录状态。

退出登录只清除这一端的凭证。后台退出不使桌面端失效，桌面端退出也不使后台 Cookie 失效。

## 5. 游戏管理

管理员可以创建和编辑游戏。创建时填写标识、名称和说明。标识创建后不能改，数据库里的游戏 Skill 用它绑定游戏。名称和说明可以改。

还有 Skill 绑定这个游戏时，不能删除该游戏。

桌面端不能创建游戏。游戏列表、名称和说明以服务端数据为准。新游戏走更新提示，用户确认后写入本机。已同步游戏的名称和说明在检查更新时直接刷新展示，不下载 zip。

## 6. Skill 管理

创建 Skill 时选择通用 Skill 或游戏 Skill，并写入数据库。通用 Skill 的游戏标识为空。游戏 Skill 必须选择一个已有游戏，把该游戏标识写入这条 Skill 记录。

Skill 的稳定标识是数据库中的 Skill id。名称在同一套官方 Skill 中唯一，创建后不能改。

保存文件有三种方式：在后台编辑说明和文件、上传文件夹、导入 zip。文件夹在浏览器里先打成 zip，服务端只接收 zip。zip 是文件本体：根目录直接包含现有约定下的 Skill 目录内容（含 `SKILL.md`），不含游戏绑定、版本列表或 registry 清单。清单字段由管理员在保存时写入数据库，不从 zip 解析。

服务端按与 `gen-mod` `validate` 相同的规则校验：`SKILL.md` 的 name、description 必须与该 Skill 记录一致；`requiredCommandScripts` 和 `inspectionFile` 若有值必须在 zip 内存在且可解析；Markdown 本地引用不得越界。校验用 D1 清单快照 + zip 内文件，不用 zip 里的 registry。

保存成功时：

- 生成文件 id（UUID），把 zip 写入 R2，对象键等于该文件 id。
- 在该 Skill 下新增一条版本记录：版本号、内容哈希、上传时间、文件 id、清单快照。
- 版本号写在版本记录里。

先写 R2 再写 D1。D1 失败则版本列表不变、不出现新版本。不要求跨存储原子事务，允许留下无引用的 R2 对象。

最新版本按上传时间计算。一个 Skill 最多 5 个版本。已经有 5 个时，再保存会被拒绝，提示先移除旧版本。同一 Skill 里版本号不能重复。内容变了但版本号没变，同样拒绝。移除版本后删除该条记录；如果没有别的版本使用同一个文件 id，再删除 R2 对象。服务端不自动丢弃旧版本。

下载接口按文件 id 返回 zip。客户端解压后再使用。

服务端不做启用开关。桌面端继续使用本机启用状态。

## 7. 桌面端同步与使用

桌面端不再用安装包内的 `registry.json` 作为官方游戏和官方 Skill 的来源。安装包不携带 Skill。官方数据以接口返回的游戏记录、Skill 记录、版本记录和文件 id 为准。选游戏、加载哪些 Skill、新会话用哪个版本，都按这些关联在客户端计算。

登录成功后检查游戏和官方 Skill 版本，工作台里也可以手动检查。发现新游戏或新的 Skill 版本时提示用户更新，并在确认前说明：

- 确认后按文件 id 下载 zip，解压到该 Skill 的新版本目录，不得覆盖当前任务正在使用的目录。
- 之后新建的会话使用这次更新的版本。
- 已经开始的任务继续使用开始时的内容哈希和当时打开的目录。
- 快照与当前已确认官方版本不同的会话变为只读，不能再发新任务。
- 本机已有的旧版本、用户导入和其他文件都保留，不会被删除。

用户拒绝或关闭提示时，不下载、也不切换新会话所用的版本。服务端已经移除的版本不再出现在更新提示里，本机对应文件保留。新会话只能使用仍在服务端版本列表中、且用户已确认的版本。同步和更新都不删除本机已有内容。

新建项目时选择游戏标识，不再选择游戏能力名。客户端按下面三条分别计算：

- **可加载集合：** 本机已启用的通用 Skill，加上绑定该游戏且本机已启用的 Skill。官方部分取用户已确认下载的版本，导入部分取本机导入。
- **新会话版本：** 可加载集合里，每个官方 Skill 各自使用该 Skill 已确认版本中上传时间最新的一条；导入 Skill 使用其本机那一份。不是全局只取一条版本。
- **允许新建项目或新会话：** 该游戏至少有一个已确认下载的官方游戏 Skill。仅有导入、没有已确认官方游戏 Skill 时，不能新建项目或新会话。

已有本机项目仍保存原来的 `gameId`。打开时按 `gameId` 走上述规则，不再用 `game_skill_name` 做 `resolve`。尚未确认该游戏的官方游戏 Skill 时，项目可以打开，会话只读，不能发新任务。确认更新后，快照与「当前每个已确认官方 Skill 的最新版本 + 当前导入」不一致的会话只读。安装包升级后资源目录不再带 Skill，不把旧安装包内置目录算作已确认官方 Skill。

用户导入仍走本机流程，不上传、也不进入官方的 5 个版本：

- 通用 Skill 符合现有目录约定即可导入。
- 游戏 Skill 所写的游戏必须存在于本机已同步的游戏管理数据中，否则拒绝导入。导入不能产生新游戏。
- 导入名称与官方 Skill 名称冲突则拒绝。

## 8. 错误处理

服务端拒绝请求时不写入半成品。先写 R2 再写 D1。D1 失败则版本列表不变、不出现新版本。不要求 D1 与 R2 的跨存储原子事务。

以下情况直接拒绝，并返回明确原因：

- 邮箱已注册、邮箱或密码不正确。
- 普通用户调用游戏管理或 Skill 管理接口。
- 创建游戏 Skill 时没有选择已有游戏，或游戏标识不存在。
- 一个 Skill 已有 5 个版本，或同一 Skill 下版本号重复。内容变了但版本号没变，同样拒绝，并提示先移除旧版本或提高版本号。
- 删除仍有 Skill 绑定时的游戏。
- zip 未通过与 `gen-mod` `validate` 相同的校验（含 `SKILL.md` 与清单快照不一致）。

桌面端只有在服务端明确判定登录凭证无效时回到登录页。检查更新、下载、导入或令牌刷新遇到网络或服务错误时，留在当前页面并提示失败，不清除登录状态，也不删除本机文件。用户拒绝更新时不下载、不切换新会话使用的版本。导入不符合现有目录约定、游戏不在已同步的游戏管理数据中、或与官方名称冲突，拒绝导入并保留用户选中的原文件。官方 zip 下载后用同一套 `validate` 规则和内容哈希校验，失败时不登记为已确认版本，不切换新会话版本，不删除已有文件。

已经开始的任务在上述任何失败或成功更新之后，仍使用开始时的内容哈希和目录。

## 9. 测试

服务端测试写在 `gen-mod-admin`，至少覆盖：

- 注册登录。
- 普通用户访问管理接口被拒绝。
- 没有游戏时仍可创建通用 Skill。
- 游戏 Skill 必须绑定已有游戏，绑定写在数据库记录中。
- 版本记录带有文件 id，下载按文件 id 取 zip。
- zip 按 `validate` 同类规则校验；清单字段来自数据库快照。
- 内容哈希与客户端下载后校验使用同一算法。
- 同一 Skill 最多 5 个版本。
- 版本号重复，或内容变了版本号没变，被拒绝。
- 仍有 Skill 绑定时不能删除游戏。
- 保存失败时版本列表不变。

桌面端测试写在 `gen-mod`，至少覆盖：

- 登录后按接口数据检查更新。
- 用户确认后才按文件 id 下载解压。
- 拒绝更新时不切换版本。
- 本机已有内容不被删除。
- 选择游戏时按可加载集合加载；每个官方 Skill 取已确认的最新版本。
- 没有已确认官方游戏 Skill 时不能新建项目或新会话。
- 已有项目按 `gameId` 加载，不再用 `game_skill_name` 做 resolve。
- 导入通用 Skill 与导入游戏 Skill 的校验，以及与官方名称冲突时拒绝。
- 确认更新后旧会话只读；进行中任务仍使用开始时的目录和内容哈希。
- 凭证明确无效才回到登录页；网络或服务错误不退出登录。

这期不测安装包发布，也不把部署到 Cloudflare 当作功能测试的一部分。

## 10. 项目初始化

两个应用都用官方脚手架生成，再放进 pnpm monorepo 的 `apps/`。不手写空项目替代官方模板。

### 10.1 后端 `apps/server`

按 [Elysia Quick Start](https://elysiajs.com/quick-start.html) 初始化。官方推荐 `bun create elysia`：

```bash
bun create elysia apps/server --no-git
cd apps/server
bun dev
```

本地开发用官方的 Bun 开发服务器。Cloudflare Workers、D1、R2 在这个脚手架之上接入，不改用另一套后端框架或另一套官方未记载的起始模板。

### 10.2 前端 `apps/admin`

按 [Vite+ Creating a Project](https://viteplus.dev/guide/create) 创建 Vue 应用。不使用 `create-vue`。本仓库包管理器是 pnpm，不装全局 `vp` 时用：

`--directory` 只适用于 Vite+ 内置模板（`vite:application` 等），`vue` 是社区简写模板，不能带 `--directory`。在仓库根执行：

```bash
pnpm create vite-plus vue --package-manager pnpm --no-git
```

把生成出来的项目目录收成 `apps/admin`。生成结果是 Vue 3 单页应用，使用 TypeScript、单文件组件和组合式 API（`<script setup>`）。开发、测试、生产构建走 Vite+ 命令（`pnpm exec vp dev` / `vp test` / `vp build`）。产物按 Workers Static Assets 发布。

不使用 Nuxt，也不使用 CDN 无构建方式。仓库已有 git，脚手架加 `--no-git`。模板若未带 Vue Router，在该脚手架之上安装 `vue-router`，不改用另一套创建工具。

### 10.3 仓库收口

根目录用 pnpm workspace 包含 `apps/admin` 和 `apps/server`。前后端共享的请求/响应类型放在工作区里，不另起第三套脚手架。

## 11. 仓库布局

```text
gen-mod-admin/
  apps/admin/     Vue 3 管理后台（Vite+ vue 模板）
  apps/server/    Elysia API（bun create elysia）
  docs/superpowers/specs/
```

本仓库前后端通过工作区共享类型。`gen-mod` 按接口返回的游戏、Skill、版本和文件 id 调整客户端逻辑，不把 Tauri 工程并进本 monorepo。
