# GenMod 管理端设计

日期：2026-10-23

本文约定 `gen-mod-admin` 第一期的范围、边界和可验证行为。实现以本文为准。桌面端改动落在 `D:\codetest\gen-mod`，不把 Tauri 应用迁入本仓库。

## 1. 背景与目标

`gen-mod` 是 Windows 本地桌面应用。玩家在本机用 AI 做游戏 MOD。项目、会话、记忆和模型 Key 仍在本机。第一期为它增加云端配套后台：账号、游戏管理、官方 Skill 发布，以及桌面端登录后按用户确认拉取官方 Skill。

成功标准：

- 玩家用邮箱和密码注册并登录桌面端，登录后才能进入工作台。
- 管理员在后台创建游戏、创建和更新官方 Skill。
- 桌面端发现新游戏或新 Skill 版本时提示用户，说明更新后果，用户确认后才下载 zip 并解压使用。
- 用户仍可按现有 Skill 规范在本机导入 Skill，但不能通过导入创建游戏。

## 2. 范围

第一期包含：

- `gen-mod-admin` pnpm monorepo：Vue 3 管理后台 + Elysia API。
- 同一套账号，角色区分普通用户和管理员。
- 游戏管理、官方 Skill 发布与版本管理。
- 桌面端登录、检查更新、确认后下载解压、本机导入约束。

第一期不包含：

- 安装包发布、自动更新安装包。
- 邮箱验证、找回密码、邀请码、第三方登录。
- 按用户分配 Skill 或游戏。
- 把桌面工作台迁到浏览器。
- 另定一套 Skill 规范。zip 和导入都使用 `gen-mod` 现有 Skill 规范。

## 3. 架构与边界

两个仓库，三条运行路径。

`gen-mod-admin` 只有两个应用：

- `apps/admin`：Vue 3 管理后台，用 Workers Static Assets 发布。
- `apps/server`：Elysia API，运行在 Cloudflare Workers 上。账号、角色、游戏和 Skill 版本存在 D1；官方 Skill 的 zip 存在 R2。

桌面端继续留在 `gen-mod`，只加登录、检查更新和确认后的下载解压。模型调用走用户自己的服务商，不经过本 API。

游戏由管理员单独创建。Skill 在创建时选择一类：

- **通用 Skill**：不绑定游戏，没有游戏也可以创建。
- **游戏 Skill**：绑定一个已经创建的游戏。没有可选游戏时，不能创建这一类。

Skill 不创建游戏。游戏记录只包含标识、名称和说明，不附带 Skill 包。

| 数据 | 位置 | 谁可以改 |
| --- | --- | --- |
| 账号、角色、游戏、官方 Skill 版本 | D1 | 注册接口、管理员接口 |
| 官方 Skill 的 zip | R2 | 编辑、上传文件夹或导入 zip 产生新版本；移除版本时删除对应对象 |
| 本机游戏数据、解压后的官方 Skill、用户导入、项目和会话 | 桌面端现有数据目录 | 用户确认后的同步，以及现有本机功能 |

管理后台和 API 是两个 Worker，生产环境放在同一主域名下。后台使用父域 HttpOnly Cookie，桌面端使用访问令牌和刷新令牌。

Workers 没有可持久化的本地磁盘。不使用 Postgres，也不把包写在服务器磁盘上。

## 4. 账号与登录

玩家和管理员使用同一套账号。注册只需要邮箱和密码。密码只在服务端保存哈希。

管理员由 Workers 密钥 `ADMIN_EMAILS` 指定。名单里的邮箱在注册或登录时成为管理员，移出名单后下次登录恢复为普通用户。

两边调用同一个登录接口，凭证不同：

- 管理后台使用父域的 HttpOnly Cookie。普通用户可以登录，但打不开游戏管理和 Skill 管理，相关接口返回 403。
- 桌面端使用访问令牌和刷新令牌，保存在本机应用配置中。访问令牌过期后用刷新令牌更换。

桌面端没有有效登录时停在登录页，不进入工作台。本机已有的项目和 Skill 文件仍留在磁盘上，登录成功后再继续使用。

只有服务端明确判定登录凭证无效时，桌面端才回到登录页。令牌刷新遇到网络或服务错误时留在当前页面并提示，不清除登录状态。

退出登录只清除这一端的凭证。后台退出不使桌面端失效，桌面端退出也不使后台 Cookie 失效。

## 5. 游戏管理

管理员可以创建和编辑游戏。创建时填写标识、名称和说明。标识创建后不能改，Skill 用它绑定游戏。名称和说明可以改。

还有 Skill 绑定这个游戏时，不能删除该游戏。

桌面端不能创建游戏。桌面端的游戏数据来自服务端，经用户确认更新后写入本机。

## 6. Skill 管理

创建 Skill 时选择通用 Skill 或游戏 Skill。通用 Skill 不绑定游戏。游戏 Skill 必须选择一个已有游戏。

保存 Skill 有三种方式：在后台编辑说明和包内文件、上传文件夹、导入 zip。文件夹在浏览器里先打成 zip，服务端只接收 zip。zip 必须符合 `gen-mod` 现有 Skill 规范，不新增字段或格式。校验通过后按内容哈希放入 R2，并在该 Skill 下新增一条版本记录。

版本记录包含：包内的版本号、内容哈希、上传时间、zip。最新版本按上传时间计算。

一个 Skill 最多 5 个版本。已经有 5 个时，再保存会被拒绝，提示先移除旧版本。同一 Skill 里版本号不能重复。内容变了但版本号没变，同样拒绝。移除版本后删除该条记录；如果没有别的版本使用同一个哈希，再删除 R2 里的 zip。服务端不自动丢弃旧版本。

下载接口只返回所选版本的 zip。客户端解压后再使用。

服务端不做启用开关。桌面端继续使用现有的本机启用状态。

## 7. 桌面端同步与使用

登录成功后检查游戏管理和官方 Skill 版本列表，工作台里也可以手动检查。发现新游戏或新的 Skill 版本时提示用户更新，并在确认前说明：

- 确认后下载对应 zip，解压到该 Skill 的新版本目录。
- 之后新建的会话使用这次更新的版本。
- 已经开始的任务继续使用开始时的内容哈希。
- 本机已有的旧版本、用户导入和其他文件都保留，不会被删除。

用户拒绝或关闭提示时，不下载、也不切换新会话所用的版本。服务端已经移除的版本不再出现在更新提示里，本机对应文件保留。同步和更新都不删除本机已有内容。

选择游戏时，加载本机已启用的通用 Skill，以及绑定该游戏且已启用的 Skill。其中既包括已确认下载的官方版本，也包括用户导入的 Skill。新会话在用户已确认的官方版本里，使用上传时间最新的一个。

用户导入仍走本机流程，不上传、也不进入官方的 5 个版本：

- 通用 Skill 符合现有规范即可导入。
- 游戏 Skill 所写的游戏必须存在于本机已同步的游戏管理数据中，否则拒绝导入。导入不能产生新游戏。

安装包不携带 Skill。官方 Skill 只来自用户确认后的下载结果。

## 8. 错误处理

服务端拒绝请求时不写入半成品。版本记录和 zip 必须一起成功；任一步失败，Skill 的版本列表不变，不出现新版本。

以下情况直接拒绝，并返回明确原因：

- 邮箱已注册、邮箱或密码不正确。
- 普通用户调用游戏管理或 Skill 管理接口。
- 创建游戏 Skill 时没有选择已有游戏，或游戏标识不存在。
- 一个 Skill 已有 5 个版本，或同一 Skill 下版本号重复。内容变了但版本号没变，同样拒绝，并提示先移除旧版本或提高版本号。
- 删除仍有 Skill 绑定时的游戏。
- 上传的 zip 不符合 `gen-mod` 现有 Skill 规范。

桌面端只有在服务端明确判定登录凭证无效时回到登录页。检查更新、下载、导入或令牌刷新遇到网络或服务错误时，留在当前页面并提示失败，不清除登录状态，也不删除本机文件。用户拒绝更新时不下载、不切换新会话使用的版本。导入不符合现有 Skill 规范，或游戏 Skill 指向的游戏不在已同步的游戏管理数据中，拒绝导入并保留用户选中的原文件。

已经开始的任务在上述任何失败或成功更新之后，仍使用开始时的内容哈希。

## 9. 测试

服务端测试写在 `gen-mod-admin`，至少覆盖：

- 注册登录。
- 普通用户访问管理接口被拒绝。
- 没有游戏时仍可创建通用 Skill。
- 游戏 Skill 必须绑定已有游戏。
- zip 按 `gen-mod` 现有 Skill 规范校验。
- 同一 Skill 最多 5 个版本。
- 版本号重复，或内容变了版本号没变，被拒绝。
- 仍有 Skill 绑定时不能删除游戏。
- 保存失败时版本列表不变。

桌面端测试写在 `gen-mod`，至少覆盖：

- 登录后检查更新。
- 用户确认后才下载解压。
- 拒绝更新时不切换版本。
- 本机已有内容不被删除。
- 导入通用 Skill 与导入游戏 Skill 的校验。
- 任务开始后内容哈希不随更新变化。
- 凭证明确无效才回到登录页；网络或服务错误不退出登录。

不另写一套 Skill 规范测试。校验用例直接使用现有规范里的合法包和非法包。这期不测安装包发布，也不把部署到 Cloudflare 当作功能测试的一部分。

## 10. 仓库布局

```text
gen-mod-admin/
  apps/admin/     Vue 3 管理后台
  apps/server/    Elysia API
  docs/superpowers/specs/
```

本仓库前后端通过工作区共享类型。`gen-mod` 桌面端按本文约定的 HTTP 行为自行实现客户端，不把 Tauri 工程并进本 monorepo。
